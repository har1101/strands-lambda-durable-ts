### npm 公開の方針: 当面は公開しない

トラブルの起きにくさを優先して、`NPM_TOKEN` は設定せず、GitHub Release の tarball で配布します。理由は次のとおりです。

- 長期間有効なトークンをリポジトリに置かないので、漏えいのリスクがありません。
- npm では、公開したバージョンを後から取り消せません（unpublish は 72 時間以内などの制限付き）。名前も一度使うと実質的に固定されます。

利用者は `npm install https://github.com/har1101/strands-lambda-durable-functions/releases/download/v0.2.0/strands-lambda-durable-functions-0.2.0.tgz` でインストールします。

将来公開する場合の手順:

1. npm の名前が空いているか確認します（2026-09-24 時点では空き）。
2. トークンを使わない npm の Trusted Publishing（GitHub Actions の OIDC）を優先して検討します。npmjs.com のパッケージ設定でこのリポジトリのワークフローを登録し、`release.yml` の publish ステップを OIDC 用に変えます。最初の公開の前に登録できるかどうかは、公開時に npm のドキュメントで確認してください（未検証）。トークンを使う場合は、`gh secret set NPM_TOKEN -R har1101/strands-lambda-durable-functions` を実行してから次のタグを push します。
3. 公開後、このリポジトリの backend の依存を `"strands-lambda-durable-functions": "^0.2.x"` に変え、README 2 つの tarball URL の注記を削除します。

## 7. 次の構想: 依存を最小限にした版（Hono のような設計）

別の作業として進める予定です。まだ着手していません。

- **動機**: 現在のライブラリは Strands の `Model`、`Tool`、`ToolExecutor` を前提にしています。Strands を使わないエージェント実装（自前のループ、Vercel AI SDK、Bedrock Converse の直接呼び出しなど）でも、同じ durable 化の仕組みを使えるようにしたいと考えています。
- **方向性（案）**:
  - コアは Strands に依存させません。依存は `@aws/durable-execution-sdk-js`（peer）だけか、それもアダプターで差し替えられる形にします。Web 標準 API だけで書き、ランタイムに依存しない Hono 風の小さなコアを目指します。
  - コアに入れる候補:
    - モデル呼び出しのステップ化（ストリームの記録と再生）
    - ツール実行のステップ化（idempotency key、リトライの分類、結果と差分の記録）
    - ツールの子コンテキストを決定的に開く仕組み（`TurnCoordinator` 相当）
    - 割り込みから callback への変換
    - チェックポイントのコーデック（`schemaVersion`、`$bytes`）
    - オフロード用の serdes
  - フレームワークとの接続はアダプター（またはミドルウェア）に分けます。例: `strands` アダプター（現在のライブラリ）、`ai-sdk` アダプター、素の関数ベースの API（`durableModel(fn)`、`durableTool(fn)`）。
  - 現在のライブラリのうち Strands に依存しない部分は、そのまま流用できる見込みです（`codec`、`retry`、`offload`、`s3`、`events`、`scope` の大半）。
- **決めること**:
  - パッケージの構成（単一パッケージのサブパス export か、`@scope/core` と `@scope/strands` などの複数パッケージか）
  - 名前（`strands-` 接頭辞は外す）
  - 現在の `strands-lambda-durable-functions` をコアの上に作り直すかどうか
  - 対象のランタイム（Lambda durable functions だけか、他の durable 実行基盤も抽象化するか）

## 9. 既知の制約

- 並列ツールが同じ `appState` のキーに書き込んだ場合、最終的な値は完了順に依存します（README に記載済み）。
- `InterruptError` は現在、`error.name === "InterruptError"` で判定しています。上流で export されたら `instanceof` に切り替えます（`src/tool.ts` の `isInterruptError`）。
- `DurableToolExecutor` は `ConcurrentToolExecutor` を継承しており、型は `Parameters<ConcurrentToolExecutor["execute"]>` で取り出しています。上流で `ToolExecutor` が公開されたら、公開型に切り替えます。
- ライブの `appState` を追跡するため、エージェントごとの `StateStore` インスタンスの `set`、`delete`、`clear` を差し替えています。Strands が StateStore の実装を変えた場合は、`test/replay.test.ts` と `test/features.test.ts` の appState 系テストで検出できます。

## 付録: ToolExecutor PR 本文の要点

- タイトル: `feat(tools): make the TypeScript ToolExecutor base public`
- 公開するもの: `ToolExecutor`（値）、`ToolExecutorOptions`、`ToolExecutionInput`（型）。
- 型の拡張: `AgentConfig.toolExecutor` と `Agent.toolExecutor` の型を `ToolExecutor | ToolExecutorStrategy` に広げます。
- 名前の変更: protected の `_storePendingToolExecution` を `storePendingToolExecution` に変えます。`strands-ts/AGENTS.md` では、`_` 接頭辞は private にだけ使う規約だからです。
- `ToolExecutorOptions` のうちエージェントだけが設定するフィールド（バックグラウンドタスクと interrupt の差し替え）は、`@internal` とし、1 行の説明を付けます。
- `execute()` の契約:
  - ツール実行ごとに結果を 1 つ push します。
  - 再開時は `completedToolResults` を再利用します。
  - `cancelSignal` を尊重します。
  - `InterruptError` のときは `storePendingToolExecution()` を呼んでから再 throw します。
- レビュアーに判断を求める点:
  - `middlewareRegistry`、`tracer`、`meter` の型が export されていない。
  - 名前の変更。
  - `executeBackground()` は internal のまま残す。
- テスト:
  - `src/tools/executors/__tests__/executor.test.ts`: 逆順に実行するスケジューラー。
  - `src/__tests__/index.test.ts`: `ToolExecutor` が export され、組み込みの 2 つのエグゼキューターの基底クラスであること。
- ドキュメント: `site/.../tools/executors.mdx` に TypeScript のカスタムエグゼキューターの節を追加します（`TimedToolExecutor` の例）。
